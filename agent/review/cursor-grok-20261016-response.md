## B. 分项核对

**数据位打包：有源码和管脚名证据，且全 1 不会被打包方式造出来。**

原理图文字写明：`PD12_LBUS-LD0` 到 `PD19_LBUS-LD7`，`PA12_LBUS-LD8` 到 `PA19_LBUS-LD15`（`schematic-text.txt` 约 1728–1762 行）。探针按这个顺序拼接：

```138:139:app/device/firmware/board.c
    return (uint16_t)(((pd >> L16_DATA_FIRST_PIN) & L16_DATA_BYTE_MASK) |
        (((pa >> L16_DATA_FIRST_PIN) & L16_DATA_BYTE_MASK) << L16_DATA_HIGH_SHIFT));
```

`L16_DATA_FIRST_PIN` 是 12。bit0 是 PD12/D0，bit8 是 PA12/D8，bit10 是 PA14/D10。LBC 路径不再改位序，只取接收 FIFO 的低 16 位（`board.c` 97 行）。源码没有把这 16 位写成 1。现场 `startupGpioProbeWord=65535` 只能说明当时 PA、PD 的 bit12..19 都是 1。之后 v15 转储里，LBC 复用已恢复，PA DATA 仍是 `0x00000001`（`pio-control-v15.txt`），数据位锁存为 0。这和“输入模式读到的是脚上的高电平”一致。

网页 `D${channel}` / `YX${channel + 1}`（`app.mjs` 479–482 行）把 YX11 标在 bit10。这只是页面假设。整字已经是 0xFFFF，任何一位若为 0，十六进制都不会仍是 65535。YX11 到底进没进 U16，文字稿没有连线，不能据此认定。

**输入复用和方向：运行中的复用与源码一致；调试文件里的 “in lo” 不是脚电平。**

`board-registers.h` 35–42 行：PA12..19 为 mux 6，PD12..19 与 PD21 为 mux 8，PA21、PD20、PK3..5 为 mux 1（输出）。v14 寄存器与此相符：`0x03604084=0x6666ffff`，`0x03604088=0xff1f6666`，`0x03604204=0x8888f1bb`，`0x03604208=0xff818888`，`0x03604580=0xff111f55`。v15 的 PA/PK 转储同样如此。

数据位没有被设成 GPIO 输出。`pinconf-live-v14.txt` 中这些脚是 input bias disabled；v15 的 PA 上拉寄存器 `0x036040b0/b4` 为 0。全 1 不是 SoC 内部上拉配出来的。

`gpio-live-v14.txt` 里数据脚显示 `in lo`，`pinmux-live-v14.txt` 显示 `GPIO`。前者是 Linux 占用这些 GPIO 时读到的数据锁存，后者是占用者名字。同一时刻原始复用已经是 6 和 8，PA DATA 的 bit12..19 为 0。不能把 “in lo” 当成总线是低电平，再去软件里找反相。

IDA 控制字 `0x00038001`（`board-registers.h` 91 行）与旧裸核读事务相同，现场 `liveErrorCode=0` 且心跳在增加，说明事务完成并反复发布。本次材料没有 SDK 手册，方向位和控制字各字段没有逐位重推。

**CS、OE、译码极性：软件写出的电平已被寄存器证实；译码器使能和缓冲器 OE 的连线没有证实。**

软件在初始化末尾把 PA21 拉低后不再改 CS（`board.c` 80–81 行），PD20 保持高，PK 设为 101：`L16_DECODE_HIGH=0x28`（PK3、PK5），`L16_DECODE_LOW=0x10`（PK4）。v14/v15：PA21 为 0，PD DATA `0x00100400` 表示 PD20 为 1，PK DATA `0x00000028`。`gpio-21 out lo`，PK3 高、PK4 低、PK5 高。

`101` 反过来仍是 `101`。即便 A0 与 A2 在 138 上接反，选中的仍是 Y5。旧代码 `AMP_BUS_DI_CHIP` 也是 5，并写明地址 7 是板址，不是这组开入（`bus_di.h` 4、21–27 行）。

文字稿能确定的器件是：U12 为 `AiP74LVC138`，Y5 是第 10 脚（2358–2378 行）；五片 `AIP74LVCH245`，DIR 为第 1 脚、OE 为第 19 脚。第三页有设计说明：DIR 高且 OE 低时 B=A，A 为输入、B 为输出（2594–2610 行）。型号本身意味着 138 的 Y、E1、E2 低有效，E3 高有效；245 的 OE 低有效，带 H 的型号有总线保持。文字稿没有写出 PA21 进了哪一个 E 脚，也没有写出 Y5 是否接到 `LBUS_CS_OUT2`，以及 YX11/12/13 是否就是 U16 的 A2/A3/A4。因此工程记录里的这条链还不能当成已核对事实。PD21 的网名是 `PD21_LBUS-OE`，软件只把它交给 LBC，不自己拉电平。

**LBC 读事务、16 位和采样时序：事务格式有源码和现场寄存器；采样沿相对 OE 没有实测。**

时序模式 `0x02011000` 已出现在 `0x02810180`。每笔长度为 1 个半字，只读 `0x350`，不写 `0x340`。读循环不改 CS、不改数据 GPIO（`board-test.c` 83–87 行把这一点做成了宿主断言）。成功窗口的首尾字是 `0xffff`（`di-1mhz-final-v13-repeat/result.json`）；另一次在 318899 点后 error 6，即 `L16_DEADLINE`，首尾仍是 `0xffff`。完成只说明读事务结束，不说明接点已进入该字。本次没有逐点扫那两兆字节，不能把中间每一个样本都说成已经核对过。

监视约每 1 ms 读一次，不写波形区（`main.c` 226–237、300–301 行）。探针在 `prepare` 成功之后做，不发 START，只把数据复用清成 0，等 24 个 tick 再读回（`board.c` 116–139 行）。它和 LBC 都是全 1。若 245 的 OE 是电平选通，探针已经在看稳态；若 OE 只在 PD21 脉冲期间有效，探针看到的是脉冲间隙，不能代表采样瞬间。

**共享状态、小端和网页位：一致，而且全 1 对字节交换不敏感。**

`live_status` 低 16 位是原码，bit16 有效，bit17 使能，错误在 bit24 起（`logic16.h` 24–27 行）。服务按小端解 36 个 uint32，`liveWord` 只在有效位为 1 时取出（`service.py` 25、195 行）。波形用 `getUint16(..., true)`（`capture-core.mjs` 64 行）。0xFFFF 高低字节相同，小端不会把某一路 0 显示成全 1。当前 `liveErrorCode=0`，所以这不是故障哨兵，也不是本地 service.py 相对 release 的 error9 判断差异。

## C. 三个优先假设和最小验证

以下只测量，不写寄存器，不 ARM，不停当前监视。CS 保持现在的低电平，数据线保持输入。

1. **选中的 245 没有把 A 侧送到总线上。** OE 为高，或 DIR 为低。B 侧被总线保持或板上拉电阻保持为高，CPU 就稳定读到 0xFFFF，接点只改变 A 侧。  
   验证：测 U14、U15、U16、U17、U18 的 19 脚 OE 和 1 脚 DIR，不要先假定是 U16。同时测 U12 的 Y5（10 脚）以及 E1/E2/E3（4/5/6 脚）。五片 OE 都为高，且 Y 全为高：译码器没打开。只有一片 OE 为低且 DIR 为高：再比这片的 8 个 A 脚和 8 个 B 脚。A 有低、B 全高，就是方向或 OE 问题。

2. **PA21 低并没有使能 138。** 地址 101 已经在脚上，但 CS 若接到高有效的 E3，或另一只使能脚不满足，所有 Y 都为高，245 关闭，结果同假设 1。A0/A2 对调不能解释这个现象。  
   验证：用万用表确认 SoC 外侧 PA21 为低、PK3/PK5 为高、PK4 为低。若脚电平与寄存器一致而 Y5 仍为高，使能条件不成立，问题在 E 脚接法，不在位打包。

3. **缓冲器已经导通，A 侧本身就是高。** CPU 如实读到高。可能是该接点此刻没有把光耦输出拉低，观察窗口内没有真正变位，或者拉低没有到达这片 245。这不能直接说成器件损坏。  
   验证：在假设 1 已确认 OE 低、DIR 高之后，看 8 个 A 脚。若全高，再只操作用户认为不同的那一路，看对应 A 脚变不变。A 变而 B 和 PA14/PA15/PA16（D10/D11/D12）不变，回到假设 1。A、B、CPU 脚一起变而网页仍是 65535，才重新查软件。直流表看不到亚微秒脉冲；只有 OE 不是稳态低、而是跟着 PD21 跳时，才用示波器同时看 PD21 和 PA14。

## D. 结论

软件根因不足以成立，也不能据此断定硬件损坏。已证实的是：复用、CS 低、WR 高、译码 101、16 位读事务完成，以及 GPIO 探针和 LBC 都得到 0xFFFF；打包、小端和网页不会把其中一位 0 显示成整字 0xFFFF。未证实的是 Y5 到哪一片 245 的 OE、PA21 到哪个使能脚、DIR 是否被拉高，以及 YX11/12/13 的实际网。SDK 手册里的 IDA 方向位和“DATA 在输入模式下是否等于脚电平”也没有原文。下一步是上面三步测量；在 A 侧与 B 侧、OE 分开之前，没有正当的软件修改点。
